# 第3回 解答

## 演習

- 第1回（素のLLM）とエージェントの回答の違い：第1回の app.ask は講座のことを知らないため、一般論で答えるしかなかった。エージェントは search_glossary で用語集を検索してから答え、「基礎（講義内容の確認）・実装（自分でコードを書く）・発展（調査や試行）の3段階で、どれか1つで完了、原則として採点はしない」と、data/glossary.json の homework-levels の定義どおりに答えた。回答の最後に「第1回」も付いた。
- `--trace` で見えたツール呼び出し（ツール名と引数）：「LoRA とQLoRAの違いは？」で `search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` の2回。docstring の「query には調べたい用語を1つだけ入れる」のとおり、用語ごとに分けて検索していた。
- 1つの質問での LLM 呼び出し回数（`requests`）：2（tool_calls=2、入力 1196 トークン、出力 216 トークン）。ツールを呼ぶ依頼で1回、ツールの結果を見て回答を作るので1回。
- 追加したツールと、docstring に書いた説明：`make_quiz(lecture: int)`。用語集から指定した回の用語を1つ選び、「『○○』の意味は？」という問題と、答え（definition）を JSON で返す。用語が無い回では、エラーにせず「用語集にありません」と返す。docstring は「指定した回（1始まりの整数）の用語から1つを選び、確認問題と答えを返す。『第2回の確認問題を出して』のように、復習用の問題を求められたときに使う。」。`--list-tools` で一覧に表示され、「第2回の内容から確認問題を 1問出して」で `make_quiz({'lecture': 2})` が呼ばれた（requests=2、tool_calls=1）。モデルは答えを伏せて「学習率」の問題だけを出した。INSTRUCTIONS の「答えそのものは書かず、ヒントで導く」の影響と考えられる。`uv run pytest -q` は 15 passed。

## 宿題

- 取り組んだレベル：基礎
- やったこと：app/tools.py の search_glossary の docstring を1か所だけ変え、同じ質問「LoRA とQLoRAの違いは？」を `--trace` 付きで実行して比べた。
  - 変更前：`query には調べたい用語を1つだけ入れる（例: "LoRA"）。`
  - 変更後：`query には調べたい用語をまとめて入れる（例: "LoRA QLoRA"）。`
- 結果：

| 項目 | 変更前（1つだけ） | 変更後（まとめて、2回実行） |
|---|---|---|
| ツール呼び出し | `search_glossary('LoRA')`、`search_glossary('QLoRA')` | `search_glossary('LoRA QLoRA')`（2回とも同じ） |
| tool_calls | 2 | 1 |
| requests | 2 | 2 |
| 入力トークン | 1196 | 1055 |
| 回答 | LoRA と QLoRA の両方を説明、第2回 | 同じ（両方を説明、第2回） |

- 気づき・疑問：
  - docstring の1文を変えただけで、モデルがツールに渡す引数の作り方が変わった。モデルは docstring を「ツールの使い方の説明書」として読んでいる。
  - まとめて検索してもツール呼び出しが1回減っただけで、requests は 2 のままだった。「ツールを呼ぶ → 結果を見て答える」の往復の回数は変わらないため。減ったのはツールの呼び出しと、入力トークン（約 12%）だった。
  - 今回は、検索が空白を無視して部分一致で探すため、「LoRA QLoRA」で両方がヒットし、回答の質は落ちなかった。ただ、検索の仕組みしだいでは、まとめた検索語が何にもヒットしないこともあり得る。docstring はツールの実装と合わせて書く必要がある。
  - 変更後の2回目の回答には、「通常は16ビットなど」のように用語集に無い説明が足されていた。INSTRUCTIONS で「推測で断定しない」と指示しても、モデルの一般知識が混ざることがある。
